# Performance investigation after IO::Async::Loop::EV 0.05

The installed upstream release fixes the callback-starvation problem. It does
not remove the HTTP throughput regression: main remains approximately 15% behind
PAGI::Server 0.002013 for GET and a small POST in these measurements. The existing
simplification branch recovers most of the streaming regression.

No Server runtime code was changed for this investigation. All variants used the
same installed IO::Async::Loop::EV 0.05, without a local adapter override.

## Upstream fix verified

The installed adapter differs from pristine 0.04 by its version and the same
`EV::idle` to `EV::timer 0, 0` change previously tested locally. The upstream
[0.05 Changes](https://fastapi.metacpan.org/v1/source/PEVANS/IO-Async-Loop-EV-0.05/Changes)
identifies busy-I/O starvation as the fix.

The existing busy-I/O regression passed against installed 0.05: both the
IO::Async-driven and native-EV-driven subtests, nine assertions each. These cover
non-inline delivery, progress under busy I/O, nested delivery on a later turn,
Future progress, cancellation, and once-only execution.

The application completion probe also passed:

| Measurement | Installed 0.05 |
| --- | ---: |
| Requests including preflight and warmup | 10,203 |
| Completion callbacks delivered | 10,203 |
| Maximum callbacks pending | 18 |
| Maximum callback delay | 7.295 ms |

The earlier 0.04 investigation observed 10,000 pending callbacks and seconds of
delay. The old local patch is now unnecessary. This verifies the observed
starvation problem, not an ordering guarantee between arbitrary event sources.

## Benchmark method

- Perl 5.42.2@default; Future 0.52 using its pure-Perl implementation;
  Future::AsyncAwait 0.71; IO::Async 0.805; Loop::EV 0.05; EV 4.37.
- One worker, EV loop, production mode, 25 clients, keep-alive,
  `LIBEV_FLAGS=8 PERL_FUTURE_NO_XS=1`.
- Same existing benchmark apps and harness for every variant. Exact-body
  preflight, including split-write POST, and successful response counts checked.
- Fresh processes, sequential runs. Initial order per workload: release, main,
  experiment, experiment, main, release. Warmup: 200 requests.
- GET and POST: 10,000 measured requests per run; stream: 5,000.
- Release: installed Server 0.002013. Main: 4625b00 plus existing release
  preparation. Experiment: `experiment/http-simplification` at 659ce38.
  Metadata records actual loaded paths and source hashes; these stayed unchanged.

These are controlled single-worker comparisons, not a reproduction of the
original 16-worker, 500-client `hey -z 30s` measurements.

## Throughput

Initial arithmetic means of two runs each, requests/second:

| Workload | Release | Main | Experiment | Main vs release | Experiment vs release |
| --- | ---: | ---: | ---: | ---: | ---: |
| GET, initial* | 3,464.0 | 2,731.6 | 2,973.2 | -21.1% | -14.2% |
| Small POST, observes connection | 3,076.9 | 2,628.9 | 2,734.6 | -14.6% | -11.1% |
| 64-chunk response | 235.6 | 216.5 | 231.2 | -8.1% | -1.9% |

*Main's initial GET samples were 2,977.6 and 2,485.5 requests/second. The second
also had a substantially higher p99. Both samples remain in the evidence; the
21.1% initial mean is not the preferred estimate of the GET regression.

To resolve that discrepancy, four longer GET runs used 30,000 requests each,
in release/main/main/release order:

| Variant | Individual rates | Mean | Difference |
| --- | --- | ---: | ---: |
| Release | 3,490.3; 3,508.8 | 3,499.5 | baseline |
| Main | 2,944.9; 2,968.0 | 2,956.5 | -15.5% |

Mean server-process CPU time was 8.89 seconds for release versus 10.49 for main:
approximately 53 additional microseconds per measured request. These process
totals include startup, preflight, warmup and shutdown; they are not isolated
request CPU timings. Mean peak RSS was 35.85 versus 37.64 MiB. The large memory
gap caused by undelivered callbacks is absent in these runs.

The experiment was not included in the longer GET confirmation. Its initial
GET rates do not establish a meaningful gain over the stable main samples.

## What the fresh profiles show

Fresh subroutine-only NYTProf runs succeeded for GET and stream on all three
variants. GET includes 2,203 requests; stream includes 703. These totals include
preflight and warmup. Timing uses elapsed wall time, and profiling amplifies
callback overhead: do not use profiled throughput as benchmark throughput or
sum profile timings to claim full attribution of the native CPU difference.

The known NYTProf/Future::AsyncAwait POST profiling failure was not retried or
worked around. The unprofiled POST benchmarks passed.

Selected call counts, with identical workload sizes across variants:

| Operation | Release | Main | Experiment |
| --- | ---: | ---: | ---: |
| GET `Future::PP::new`, total | 8,878 | 8,878 | 8,878 |
| GET `Future::PP::on_done`, total | 53 | 4,459 | 53 |
| Stream `Future::PP::on_done`, total | 53 | 45,748 | 53 |
| `_mark_complete`, calls/request | 1 | 2 | 2 |
| Deferred terminal delivery, calls/request | 0 | 1 | 1 |
| Stream HTTP send validation, calls/request | 65 | 65 | 65 |

The 53 common `on_done` calls belong to setup/connection handling. Main adds
one registration for every HTTP send: two per GET and 65 per streamed response.
The experiment moves successful-send completion into the existing async body,
removing that wrapper and callback. That concrete reduction is consistent with
the much smaller streaming gap; the experiment also contains two other changes,
so the combined benchmark is not a measurement of this change alone.

Main also adds work around each request:

- More closure construction in receive/send setup and a per-request abort hook.
- Completion at terminal output, waking a parked receiver, plus the guarded
  completion call when the application returns.
- Deferred terminal notification and cleanup through the loop.
- Checks for discarding unread request bodies after application return.

Several of these implement required correctness. Their existence is not proof
that they can be deleted. The second completion call is guarded; callbacks are
not delivered twice.

The stream write-buffer-size calculation is a large absolute hotspot, but its
90,687 calls are identical across all three variants. It does not explain the
new regression. Likewise, GET Future allocation counts did not increase.

## Recommended next step

The evidence supports a distributed request-lifecycle cost rather than another
single starvation bug. It does not yet attribute every percentage point.

Keep the successful send-wrapper simplification as a candidate. Next, examine
whether the receive implementation can be shared instead of repeatedly building
helper closures. This should simplify the ordinary receive path used by POST
and real applications, without adding a switch to skip work for hello-world.

There is a tradeoff in the existing experiment: hoisting the async receive
closure once per scope avoids rebuilding it on repeated receive calls, but also
constructs it for GET requests that never receive. Its profiled factory cost is
higher than main's. A shared implementation could avoid both forms of repeated
construction, but that remains a hypothesis to test.

Any such refactor must preserve weak connection ownership across awaits,
per-scope state, cancellation, parked receives, and terminal delivery. Do not
replace weak captures with a strongly held `$self` casually. Do not remove
deferred notifications, validation or unread-body handling to improve a score.

## Evidence and reproduction

[post-ev-005-data](post-ev-005-data/) contains the work map, driver, adapter
identity/hash, summary scripts, all run metadata, raw benchmark output, process
resource measurements, completion probe log, and extracted profile records.
Large raw NYTProf binaries remain under `/tmp/pagi-resume-20260923/profile`.

The driver imports the existing `profiling-data/profile.py` harness. To rerun
from a writable copy of the evidence directory:

```sh
perlbrew exec --with perl-5.42.2@default python3 -B run-investigation.py bench
perlbrew exec --with perl-5.42.2@default python3 -B run-investigation.py confirm
perlbrew exec --with perl-5.42.2@default python3 -B run-investigation.py profile
python3 -B summarize.py
```

The busy-I/O regression used
`prove -v /tmp/pagi-ev-timer-20260923/later-busy.t` under the same perlbrew
environment; a copy is included with this evidence. The completion probe used
the existing `profiling-data/completion-get.pl`, main, mode `off`, 10,000
requests, and the same harness.

No full Server test suite was rerun for this evidence-only update. The installed
adapter regression and benchmark preflights ran this turn. Earlier full-suite
results for the simplification branch are separate historical evidence.
