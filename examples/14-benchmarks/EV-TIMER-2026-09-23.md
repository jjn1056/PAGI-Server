# EV zero-delay timer experiment — 2026-09-23

**Result:** changing one line in an isolated IO::Async::Loop::EV 0.04 copy
removes the observed deferred-callback starvation. Callback latency and peak
memory improve substantially. Throughput changes are small; this does not
recover the original roughly 20% release-to-main throughput loss.

## Change and isolation

```diff
-   my $w = EV::idle sub {
+   my $w = EV::timer 0, 0, sub {
```

The watcher deletion and callback invocation remain unchanged. The installed
adapter still matches the pristine CPAN release. An explicit PERL5LIB override
selects the candidate only for experimental child processes. PAGI runtime code,
root main's release preparation and the PAGI spec were not changed. No dependency
was installed and nothing was pushed or submitted upstream.

The patch, regression test, commands, metadata and measurements are in
`ev-timer-data/`. The temporary runnable source copies are under
`/tmp/pagi-ev-timer-20260923/{pristine,candidate}`. See the saved work map for
repository and branch ownership.

## Correctness checks

- New continuously-readable-pipe regression fails on pristine 0.04 and passes
  with the one-line change. Both IO::Async-driven and native-EV-driven execution
  are tested. It checks non-inline delivery, busy-I/O progress, Future progress,
  callback/Future cancellation, nested deferrals waiting for another iteration,
  and once-only delivery (nine passing assertions per driver).
- Full released adapter suite: **13 files, 121 tests, PASS**, 16 seconds. It emits
  an unsupported-is_running diagnostic; the suite passes.
- Targeted PAGI-Server suite with the candidate adapter and IO_ASYNC_LOOP=EV:
  **12 files, 95 tests, PASS**, 21 seconds. Covers connection state, deferred
  terminal callbacks, graceful shutdown, reentrant cancellation, SSE close and
  refusal, HTTP/2 state and refusal, and WebSocket close parity/single-frame
  behavior. This is not a new full Server suite run.
- All benchmark preflight response checks passed, including a split-write POST.
  All measured requests returned HTTP 200 and the expected response count.

## Application-level callback probe

Same main Server code, one EV worker, 25 clients, 10,000 measured requests after
three preflight and 200 warmup requests. The app registers on_complete and counts
callbacks without wrapping loop internals or using a profiler. One run per
adapter, independent of the throughput comparison below.

| Metric | Pristine idle adapter | Timer candidate |
| --- | ---: | ---: |
| Completed callbacks at entry to request 10,000 | 203 | 9,989 |
| Peak outstanding callbacks | 10,000 | 17 |
| Maximum request-entry-to-completion-callback delay | 3.148 seconds | 7.098 milliseconds |
| Final callbacks / requests | 10,203 / 10,203 | 10,203 / 10,203 |
| Peak RSS | 81.30 MiB | 37.32 MiB |

The delay includes request handling; it is not a timer-only measurement.
Pristine callbacks eventually run after load subsides. The candidate makes
progress during load instead of accumulating the entire measured batch.

## Controlled throughput comparison

Perl 5.42.2@default, IO::Async 0.805, EV 4.37, Future::PP, production,
LIBEV_FLAGS=8, PERL_FUTURE_NO_XS=1. Same root main Server sources and existing
benchmark apps throughout; one worker, 25 clients, 10,000 measured requests per
run. Each workload uses pristine/candidate/candidate/pristine order with fresh
server processes, 200 warmup requests, and response preflight. No profiling,
other benchmark or test suite ran concurrently with the measured comparisons.

Values below are arithmetic means of two runs per adapter. This is a small
controlled comparison, not a statistical claim of a throughput improvement or
a reproduction of the original 16-worker/500-client benchmark.

| Workload | Idle req/s | Timer req/s | Change | Idle/timer peak RSS MiB | Idle/timer CPU seconds |
| --- | ---: | ---: | ---: | ---: | ---: |
| Small GET | 3,216.6 | 3,212.0 | -0.14% | 75.86 / 36.89 | 3.475 / 3.420 |
| Small POST with completion observer | 2,787.2 | 2,862.8 | +2.71% | 80.09 / 37.76 | 3.955 / 3.810 |

## Remaining ordering question

The timer candidate restores progress but does **not** reproduce Poll/Select's
exact after-current-I/O ordering. In the scheduling probe:

- An initially queued callback runs before I/O in round 1.
- A callback queued by round-1 I/O runs in round 2.
- A callback nested inside that deferral runs in round 3.

This matches the UV adapter observed in the preceding research. It preserves
the non-inline delivery required by PAGI, and the tested PAGI paths pass.
However, IO::Async's documented watch_idle contract describes delivery after
the current I/O round. Existing adapters' differing ordering is not proof that
the wording can be ignored. The candidate should be reviewed with the maintainer
before treating it as a complete upstream fix.

No priorities, alternate queue, server workaround or additional patch was added
to address that question. The next decision is whether the maintainer accepts
the timer semantics or wants strict after-current-round ordering. The observed
PAGI backlog is resolved in either case only if the chosen mechanism makes
progress under sustained I/O.
