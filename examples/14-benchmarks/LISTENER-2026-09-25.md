# Listener batching: connection admission and tail latency

## Outcome

Retain the isolated listener change with a batch limit of 64. It removes the
multi-second first-response tail at 500 connections, and the full enabled
suite passes. The size sweep supports 64 as a useful starting default; it is
not a protocol requirement or a universal optimum. No public tuning option
has been introduced.

This is PR #13's listener change (commit `7ce3c0b`), adapted to the current
`experiment/http-simplification` branch at `2e42135` (runtime checkpoint
`cdf4a7c`). It does not import the other PR optimizations. Runtime differences
are only the new `PAGI::Server::Listener` and its three construction sites in
`Server.pm`. No connection/send/state code changed.

## Why the listener matters

Stock IO::Async::Listener accepts one socket per readiness event. Under load,
500 queued connections can therefore wait across hundreds of event-loop
iterations. The private subclass accepts up to 64 per event, then yields.
It also dispatches the cleartext stream directly, avoiding the stock acceptor's
Future wrapping. A batch-size-1 control in the follow-up separates that simpler
accept path from the effect of accepting several connections per event.

The original PR loop continued after an accept callback paused, closed or
removed its listener. The candidate adds one post-callback check of handle,
read readiness and loop membership. Real-socket tests fail before that guard
and pass after it. TLS listeners using the SSL listen extension keep the stock
class. Workers already perform SSL upgrade after raw accept and can batch the
raw sockets; inherited single-worker routing remains as before.

[Original listener change in PR #13](https://github.com/jjn1056/PAGI-Server/commit/7ce3c0be04037fc154aec05c993b935dd7340b53).

## Main AWS comparison

Same standalone c7a.xlarge, Perl 5.42.2, IO::Async::Loop::EV 0.05, pure-Perl
Future and epoll as the previous controlled runs. One server worker on CPU 0,
driver/telemetry on CPU 1, clients on CPUs 2–3. Source and dependency hashes are
recorded. These are AWS performance measurements; local suite timings are not
included. Each latency entry is the median of individual runs' reported
percentile. The worst column is the largest request time across those runs.

### Burst of 500 new connections under established traffic

Five rotated rounds per variant. A separate 100-client keep-alive load runs
for 30 seconds. Two seconds into it, 500 clients each issue one request on a
fresh connection. All 500 first responses are measured separately. They are
not diluted into the much larger established-request population.

| Variant | p95, ms | p99, ms | Run p99 range, ms | Worst request, ms |
| --- | ---: | ---: | ---: | ---: |
| CPAN release 0.002013 | 3,109.40 | 3,263.50 | 3,086.70–3,362.80 | 3,392.10 |
| Saved cdf4a7c | 3,417.20 | 3,561.00 | 3,531.30–3,626.90 | 3,665.00 |
| Listener, batch 64 | 232.80 | 234.00 | 212.60–243.70 | 244.00 |

Background traffic's median p99 was 13.3 ms for release, 14.8 ms for saved and
13.3 ms for batch 64. Batch 64's first-response p99 improves about 93.4% against
saved in this workload. The burst client's requests/sec describes completion
of that fixed batch, not sustained server capacity, so it is not presented as
a throughput gain.

### Sustained GET at 500 concurrent clients

Three rotated twenty-second runs per variant, using `hey -c 500`. The harness
also performs a separate one-second warmup; timed clients then establish their
own connections. These results therefore include a connection ramp. Most
requests subsequently reuse those connections, which makes aggregate p95/p99
much less sensitive to the small number of very slow first requests.

| Variant | p95, ms | p99, ms | Run p99 range, ms | Worst request, ms |
| --- | ---: | ---: | ---: | ---: |
| CPAN release 0.002013 | 74.00 | 74.80 | 74.60–76.10 | 9,434.80 |
| Saved cdf4a7c | 82.40 | 82.60 | 81.70–84.00 | 10,978.00 |
| Listener, batch 64 | 75.40 | 76.70 | 76.70–77.30 | 238.90 |

The worst observed request falls from about 11 seconds to 239 ms. Ordinary
request p95/p99 improve more modestly. The candidate's run p99 range is
76.7–77.3 ms, versus saved's 81.7–84.0 ms in this small sample.

### Connection churn and established-connection controls

Churn uses `hey -disable-keepalive -c 100`, three fifteen-second runs per
variant. Other controls use two ten-second runs; HTTP concurrency is 25 and
WebSocket uses 20 persistent clients. Rates are completed HTTP requests/streams
per second, or WebSocket messages per second. They are compared only within
each workload.

| Workload | Release | Saved | Batch 64 | Change vs saved |
| --- | ---: | ---: | ---: | ---: |
| GET, 500 clients | 6,960.38 | 6,190.76 | 6,686.76 | +8.01% |
| Fresh connection/request, 100 clients | 2,739.95 | 2,618.07 | 3,458.28 | +32.09% |
| GET, 25 clients | 8,646.11 | 7,896.76 | 7,861.45 | -0.45% |
| POST observer, 25 clients | 7,540.30 | 7,062.92 | 7,170.38 | +1.52% |
| Chunked stream observer, 25 clients | 509.76 | 488.92 | 481.10 | -1.60% |
| SSE, 25 clients | 214.68 | 212.03 | 207.44 | -2.16% |
| WebSocket, 20 persistent clients | 12,672.88 | 12,142.15 | 12,346.86 | +1.69% |

Churn's median p95/p99 falls from 38.6/38.7 ms to 31.5/32.2 ms. Its largest
request across all runs is 45.3 ms saved and 44.5 ms candidate. Ordinary
keep-alive GET and POST are nearly level in these short samples. Streaming
throughput is 1.6% lower and SSE 2.2% lower; those small differences are retained
in the record, not excluded. Streaming p95 rises about 1 ms, and SSE p95 about
3 ms. SSE p99 falls from 149.35 to 121.75 ms. WebSocket RTT p99 is essentially
level (about 2.1 ms); its single-process client may limit throughput.

The result supports reducing connection-admission delay, not a claim to remove
all request-latency variation or make every workload faster. Tests use one
worker on Linux with CPU affinity. Multiworker and TLS paths were checked for
correctness, not benchmarked for capacity or tail latency here.

## Batch-size sweep

Eighteen additional runs, executed after the main comparison. Three rotated
rounds compare release, saved, and custom-listener limits of 1, 16, 64 and 256.
The workload remains 500 fresh connections with 100 established clients. The
background window here is 12 seconds, so these background percentiles are
kept separate from the main comparison's 30-second windows. Only the private
batch constant changes between custom-listener variants.

| Variant | First-response p95, ms | First-response p99, ms | Run p99 range, ms | Background p99, ms |
| --- | ---: | ---: | ---: | ---: |
| CPAN release | 3,182.40 | 3,301.70 | 3,206.30–3,315.40 | 13.60 |
| Saved checkpoint | 3,526.50 | 3,674.00 | 3,512.10–3,791.10 | 15.30 |
| Custom listener, batch 1 | 3,395.90 | 3,535.00 | 3,466.80–3,736.60 | 14.70 |
| Batch 16 | 362.10 | 377.40 | 344.50–382.40 | 23.80 |
| Batch 64 | 212.60 | 222.90 | 216.60–231.00 | 13.60 |
| Batch 256 | 201.20 | 202.80 | 199.30–216.20 | 13.60 |

Batch 1 retains the multi-second wait, which supports batching as the main
mechanism behind the dramatic improvement. Increasing from 64 to 256 improves
median first-response p99 another 20 ms in this workload, while allowing four
times as many accepts per callback. That is a much smaller gain than moving
from 1 to 64. Background p99 is not monotonic with batch size here; batch 16 has
the highest value among the batched variants.

Keep 64 as the tested starting value. A future tuning option is reasonable
because callback cost, existing traffic and workload shape can change the
tradeoff. This narrow GET sweep does not determine the best value for every
application, transport or machine. It does not establish an elapsed-time bound
for any of the batch sizes.

## Verification and provenance

- Local focused suite: 11 files / 65 tests, covering TLS, multiworker, limits,
  Unix/multiple listeners, inherited descriptors and activation.
- Linux listener regressions: 2 files / 8 tests.
- Full enabled local suite: **182 files / 1,282 tests**, 1,049 seconds. Opt-in
  release/stress tests and gated cross-distribution tests remain skipped as
  configured. Command: `perlbrew exec --with perl-5.42.2@default env PERL_FUTURE_NO_XS=1 prove -lr t`.
- Main comparison: **24 completed smoke runs and 63 timed runs**.
- Lifecycle tests cover pause, close and removal during an accept callback;
  an error test distinguishes EAGAIN from EMFILE and checks socket/errno delivery.
- Independent review found the lifecycle defect, then reviewed the correction
  and found no remaining blocker in its scope. Existing Server accept-error
  callback/configuration issues were identified as pre-existing and unchanged;
  see `listener-data/review.md`.

The first smoke attempt used 500 clients with a three-second deadline and timed
out on release. That attempt is preserved. Completed smoke uses 50 clients for
its five-second storm check; all timed storm comparisons still use 500. One
focused-test command named a nonexistent file and was corrected. The first
EMFILE fixture patched a socket superclass and broke IO::Socket::IP's wrapper;
the corrected fixture injects at the concrete socket class. Logs distinguish
these setup mistakes from the intentional failing regression checks.

`listener-data/` records source identities, the patch, work map, review, tests,
benchmark drivers and raw results. The batch-size variants change only the
private constant. The main and sweep summaries preserve every individual
sample. Do not pool their background percentiles because the windows differ.

All 24 completed smoke runs and 81 timed runs passed; source and loaded
dependency hashes stayed unchanged. Main timed runs returned 2,559,552 measured
HTTP responses, plus 3,598,352 background responses, and checked 743,311
WebSocket echoes. The sweep returned 9,000 first responses plus 1,671,336
background responses.

There were no listen-queue overflows or drops in the host's cumulative counters
at the end, including the failed initial smoke attempt. The kernel queue limit
was 4,096 and the server backlog remained 2,048. Thus this run demonstrated a
long admission wait without reproducing the queue-overflow/retransmit component
of the older PR's field report.

All 1,169 main and 227 sweep interval vmstat samples reported zero swap-in,
swap-out and steal. Main I/O wait peaked at 6%; sweep I/O wait remained zero.
Per-process resource logs and all raw samples are preserved. No sample was
excluded from the completed comparisons.

AWS confirmed instance `i-077635273be935c19` stopped after the results were
downloaded and checked. All work stays on `experiment/http-simplification`;
nothing was pushed or merged into PR #13.
