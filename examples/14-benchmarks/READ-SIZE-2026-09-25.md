# Read-only I/O size comparison — 2026-09-25

## Finding and disposition

**Adoption update, 2026-09-25:** The working server now defaults to 65536-byte
reads and 8192-byte writes, with independent `read_buffer_size` /
`write_buffer_size` options and matching CLI flags. See the
[tuning guide](README.md#tuning-io-chunk-sizes) for workload choices. The
experiment and deferred decision described below are the historical record;
measurements and candidate patches are unchanged.

Larger reads alone retain the large-upload gain and leave bulk-download behavior
near saved code. They do not eliminate the mixed-traffic tradeoff: under
competing uploads, small-request throughput falls and tail latency rises.
Keep the runtime defaults unchanged while choosing that workload tradeoff;
both exact candidate patches are preserved. No new public option was added.

Compared with saved code, read-only 64 KiB gives about 4.2 times the isolated
1 MiB upload rate. With competing small GETs, upload rate rises from 25.17 to
156.54 req/s, small GET rate falls 6.6%, and their p99 rises from 17.15 to
19.95 ms. In the download mixture, changing both settings nearly triples bulk
throughput while small GET rate falls 10.8%; changing reads alone stays much
closer to saved behavior (small GET rate -2.5%, p99 +0.2 ms).

These are allocations of capacity under saturated, closed-loop traffic. The
faster bulk clients offer more bytes per second, so this does not show the
same penalty under a fixed offered bulk-byte rate. Larger chunks are a useful
bulk-transfer tuning choice, but the evidence does not establish a universally
better default or an optimal chunk size.

## Workloads and boundaries

The primary comparison reuses the preceding buffer experiment's harness and
apps. Uploads use 1 MiB bodies; single-send downloads use 64 KiB. Each mixed
workload has 25 bulk clients and 100 small GET clients sharing one server.
Small responses run for twelve seconds, starting 0.5 seconds before the
10-second bulk window. Their statistics include time outside the overlap.
The mixed-upload app consumes and counts the request body while its /small
path returns the same tiny fixed response used in other checks.

GET500 uses fifteen-second runs; other timed cases use ten. There is a separate
one-second HTTP warmup. Timed clients create their own connections, so GET500
includes connection admission rather than a barrier that establishes all
connections before timing. The four-way comparison does not answer the earlier
sixteen-worker scaling question. WebSocket, SSE and small POST are smoke checks
for read-only here; their timed combined-buffer controls remain in the
[initial experiment](BUFFER-SIZES-2026-09-25.md).

Only `read_len => 65536` differs in the read-only candidate. The combined
candidate also sets `write_len => 65536`. Autoflush, read_all/write_all,
watermarks, terminal semantics and logging remain unchanged. No new git branch
or worktree was created; local runtime remained unchanged during manual testing.

## Correctness, resources and provenance

Same isolated c7a.xlarge, Perl 5.42.2, IO::Async::Loop::EV 0.05, epoll and pure
Perl Future. One server worker on CPU 0, clients on CPUs 2–3, driver/telemetry on
CPU 1. No dependency change or concurrent profiler. Client and server share a
host; these are Linux measurements, not the user's sixteen-worker Mac runs.

- Read-only focused correctness: 11 files / 78 tests passed. The two HTTP/2
  files skipped because the required binding is unavailable; TLS, HTTP request
  bodies/streaming, SSE and WebSocket checks ran. No full-suite claim is made
  for either unadopted buffer candidate.
- Primary follow-up: 8 read-only smoke runs and 56 four-way timed runs passed.
- Final mixed-upload follow-up: 1 read-only smoke and 8 four-way timed runs passed.
- Source and loaded dependency hashes remained unchanged. The local runtime
  matches the saved source hashes. Neither patch was applied to it.
- Primary timed runs returned 2,466,626 foreground and 1,032,522 background HTTP
  responses. Mixed-upload runs returned 7,347 foreground and 626,997 background
  responses. No failed benchmark samples were omitted.
- All 737 primary and 109 mixed-upload interval vmstat samples had zero swap-in,
  swap-out and CPU steal. Peak I/O wait was 7% and 2%, respectively.
- During isolated large uploads, median peak server RSS was about 41.8 MiB
  saved, 48.0 MiB with both settings enlarged, and 48.0 MiB with larger reads
  alone. These process peaks include startup/preflight; they are not a claimed
  per-connection allocation formula. Raw per-run resource logs are retained.

Across the initial experiment and both follow-ups, 36 smoke and 133 timed runs
completed successfully. All three datasets remain separate. AWS was stopped
after downloading and validating the evidence.
