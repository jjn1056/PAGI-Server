# Server baseline — 2026-09-22

This is a baseline before any performance optimization. The same five raw PAGI
apps were run against installed **0.002013** and checkout **0.002014** at
`4625b006aa136844ab80f9163bcffc25db748cb3`. Checkout runtime changes at measurement
time were release version declarations only. The existing hello example was
not used or changed by this benchmark work.

## Conditions

- macOS 15.6.1, x86_64, 16 logical CPUs; client and server on the same machine.
- Perl 5.42.2@default; EV, production, `LIBEV_FLAGS=8`, `PERL_FUTURE_NO_XS=1`.
- One-worker HTTP/SSE: 50 concurrent clients. Sixteen-worker HTTP/SSE: 500.
- WebSocket: 20 persistent connections in both configurations, one outstanding
  128-byte binary message per connection, one client process.
- Every case uses release → main → main → release: two ten-second measured runs
  per version, each after a one-second warmup. Separate server per sample.
- HTTP payloads and SSE event order/data checked before each run. Split POST
  preflight uses two 512-byte writes, 20 ms apart. Every measured WS echo checked.
- HTTP/SSE load checks completion and status, not every response payload.
- An existing user-owned 16-worker server was left running and was observed idle
  during a process snapshot. Host load is uncontrolled; these are screening
  measurements, not isolated laboratory capacity results.

Commands from the repository root:

```sh
perlbrew exec --with perl-5.42.2@default python3 examples/14-benchmarks/run.py \
  --output /tmp/pagi-baseline-20260922-w1 --seconds 10 --workers 1 --concurrency 50
perlbrew exec --with perl-5.42.2@default python3 examples/14-benchmarks/run.py \
  --output /tmp/pagi-baseline-20260922-w16 --seconds 10 --workers 16 --concurrency 500
```

`single` and `stream` both return 64 KiB; only the number of body sends differs
(one versus 64), along with the resulting transfer framing. `observe` registers
one completion callback. SSE rate is completed 100-event streams/sec; multiply
by 100 for events/sec. WebSocket rate is validated echoes/sec. Latencies in the
tables are the arithmetic means of per-run p50/p99 values, not pooled percentiles.

## Reading these results

All 80 measured samples completed with no reported load-generator request errors
or non-200 HTTP/SSE statuses. Every preflight payload check and measured WebSocket
echo passed. The in-process example checks and focused harness checks also passed.

The consistent concern is short HTTP work: POST is slower at both worker counts,
including when a completion callback is registered. This is not confined to an
app that never calls receive. At 16 workers the GET/POST declines are approximately
15–19% without cherry-picking the observer variants. The 64-send response also
shows a decline (13% at 16 workers), whereas the single-send 64 KiB case does not
show a consistent regression across worker counts.

Finite SSE streams are essentially unchanged in these samples. WebSocket results
change direction between the worker configurations and the one-worker samples
vary substantially; they do not establish a stable WebSocket regression or gain.
The small positive percentages elsewhere should likewise not be called wins.

Callback-on/off cases were measured in separate time windows. For example, the
16-worker release POST-with-observer average exceeds the no-observer average.
That is evidence of run variation, not a claim that adding callbacks speeds up
the server. This baseline supports targeting HTTP overhead, but does not assign
causality to one method or validate either proposed optimization. Repeat longer,
paired measurements when assessing a fix.

## Saved evidence

The adjacent `baseline-data/` directory contains every measured sample and its
run metadata. Raw client reports and server logs remain under the two `/tmp`
output directories above and are also preserved locally under
`local/benchmarks/2026-09-22/` (ignored by Git).

Use `summarize.py baseline-data/*results.jsonl` to regenerate the tables.
See [README.md](README.md) for workload details, manual commands, and limitations.
No server performance changes, commits, release tags, or pushes were made as
part of this baseline task.
