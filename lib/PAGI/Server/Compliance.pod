=head1 NAME

PAGI::Server::Compliance - HTTP/1.1, HTTP/2, WebSocket, SSE, and Security Compliance Documentation

=head1 DESCRIPTION

This document details the compliance testing results for PAGI::Server against
HTTP/1.1 (RFC 7230/7231), HTTP/2 (RFC 9113), WebSocket (RFC 6455), Server-Sent
Events, and common security attack vectors.

PAGI::Server demonstrates full HTTP/1.1 compliance, 93.8% HTTP/2 conformance
(matching the nghttp2 library ceiling), strong security posture, stable resource
management, and 71% WebSocket RFC 6455 compliance.

=head1 PAGI SPECIFICATION SUPPORT

PAGI::Server implements HTTP/WebSocket/SSE sub-specification B<0.6> of
L<PAGI::Spec::Www>; every http, websocket and sse scope reports
C<< $scope->{pagi}{spec_version} >> as C<'0.6'>. The core PAGI version
(C<< $scope->{pagi}{version} >>) is independent of it and remains C<'0.5'>.
See L<PAGI::Upgrading> for what changed for applications.

Of the capabilities the spec leaves optional, PAGI::Server implements, on
both HTTP/1.1 and HTTP/2:

=over 4

=item * B<Transport flow control> (C<pagi.transport>) on http, sse and
websocket scopes (see L</"Transport Flow Control (pagi.transport)">).

=item * B<WebSocket over HTTP/2> (RFC 8441 Extended CONNECT), including
per-stream C<websocket.keepalive> (see L</"WebSocket over HTTP/2 (RFC 8441)">).

=item * B<The C<tls> extension> -- certificates, negotiated version and cipher
suite on TLS connections.

=item * B<The C<fullflush> extension> on http and sse scopes (which scopes
advertise it is a ruling; see L</"PAGI SPECIFICATION RULINGS">).

=back

The lifespan protocol runs in C<auto> or C<on> mode; see C<lifespan_mode> in
L<PAGI::Server>.

Outbound events are validated against the spec and malformed ones rejected
unconditionally, on every send path, in every environment.

=head1 PAGI SPECIFICATION RULINGS

L<PAGI::Spec::Www> 0.6 leaves a small number of behaviours to the server. This
section records, in one place, how PAGI::Server decides each of them, so that a
framework or application built on this server knows what it will observe. Each
ruling names the spec text that leaves it open and the test that pins the
choice. Nothing here restates a rule the spec already makes; for those, read
the spec.

=over 4

=item * B<C<receive()> after a completed refusal parks.>
L<PAGI::Spec::Www/"Meaning per scope"> says what a C<receive()> call returns
after a completed refusal is unspecified. PAGI::Server returns a Future that
never resolves, on both transports, because the scope ended cleanly and there
is no event left to deliver. A "drain until disconnect" receive loop will
therefore hang on a refused handshake or stream; a framework must end such a
scope on C<on_complete> / C<response_complete>. Pinned by the C<post> rows of
C<t/70-protocol-disconnect-matrix.t> and by C<t/73-denial-retention.t>, which
also shows that the parked Future, the application coroutine and the scope
are all released once the application returns.

=item * B<An accepted WebSocket the application abandoned, on HTTP/2, gets the
1011 Close frame and then C<END_STREAM>, not a reset.>
L<PAGI::Spec::Www/"Application Left a Response Incomplete"> says the server
sends a Close frame with code C<1011> and then closes the transport ("the
stream, on HTTP/2"). PAGI::Server sends the frame in a C<DATA> frame that
carries C<END_STREAM>, exactly as the application's own C<websocket.close>
does. That is not a PAGI::Server choice: RFC 8441 section 5 maps an orderly
WebSocket close to C<END_STREAM> and reserves C<RST_STREAM> for the analog of
a TCP reset, and a reset issued after the Close frame is queued discards the
frame, so the client would see C<1006> instead of C<1011>. A
refusal abandoned before its terminal body, by contrast, is reset with
C<RST_STREAM> C<INTERNAL_ERROR>: no socket was accepted, so it is an ordinary
incomplete HTTP/2 response. Pinned by C<t/http2/42-d13-incomplete-session.t>.

=item * B<No wait for the peer's Close after a server-sent 1011.> The spec
allows the server to wait "no longer than its ordinary close timeout" for the
peer's Close. PAGI::Server flushes the frame and ends the transport at once
on both transports; it does not arm a timer for the peer's reply. Pinned on
HTTP/1.1 by C<t/69-connection-state-protocol-scopes.t> (the 1011 frame on
the wire) and on HTTP/2 by C<t/http2/42-d13-incomplete-session.t>.

=item * B<C<RST_STREAM> error codes.> Where the spec says "e.g.", PAGI::Server
uses C<CANCEL> for an C<abort> (the application is no longer interested in
the stream) and C<INTERNAL_ERROR> for an incomplete or unanswered response.
Both follow the code semantics of RFC 9113 section 7 (C<CANCEL>: the stream
is no longer needed; C<INTERNAL_ERROR>: an unexpected condition), and for a
WebSocket stream RFC 8441 section 5 names C<CANCEL> for the reset case.
Pinned by C<t/http2/41-abort.t> and C<t/http2/24-incomplete-response.t>.

=item * B<C<disconnect_detail> contents.> The spec makes the detail a SHOULD
with an unspecified format. PAGI::Server supplies one on every server-detected
abnormal end: the violated rule for C<protocol_error>, the queue limit for
C<queue_overflow>, the elapsed interval for C<keepalive_timeout> and
C<idle_timeout>, the byte limit for C<body_too_large>, the OS error text for
C<read_error> and C<write_error>, the C<RST_STREAM> error code for an HTTP/2
C<client_closed>, the application's exception message or a one-line
description for C<server_error>, and the application's own string for
C<app_abort>. Pinned across C<t/69>, C<t/71>, C<t/72> and C<t/http2/31>.

=item * B<Error logging.> The spec says the server SHOULD log an incomplete
response or a missing response at error level. PAGI::Server logs exactly one
line per such scope, names the condition and the transport, and logs nothing
when the client had already disconnected or the application ended the scope
with C<abort>. Every conformance suite above asserts the exact count of such
lines, so an unasserted line is a test failure.

=item * B<Extension advertisement is truthful.> The spec does not say which
extensions a scope's C<extensions> hash should name. PAGI::Server names only
those the connection can honor for that scope type: C<fullflush> is passed
through to http and sse scopes but never advertised on a websocket scope,
which has no send arm for it; C<tls> is injected on TLS connections and
removed on non-TLS ones regardless of configuration; any other configured
key passes through unchanged. Pinned by C<t/07-extensions.t>, C<t/08-tls.t>
and C<t/http2/29-fullflush-cancel.t>.

=item * B<Access log for an aborted handshake.> An C<abort> before
C<websocket.accept> or C<sse.start> produces no HTTP status, and the access
log records the status field as C<->. Observed in C<t/72-abort.t> row 1.

=back

Behaviours the spec fixes are not listed here; the relevant sections below
say what this server does and which test proves it, and the spec says why.

A server may also enforce more than the spec requires, provided the extra
check never contradicts a rule the spec does make: rejecting a send or a
receive the spec leaves unspecified is allowed, delivering an event the spec
says is not delivered is not. PAGI::Server currently adds no such checks
beyond the ones listed above; if it does in future, they will be recorded
here as rulings, each with the spec text that leaves the room. A behaviour
that does contradict the spec is not a ruling at all -- it is recorded under
L</"Deliberate Deviations">, with the option that switches it off.

=head2 Deliberate Deviations

One behaviour below departs from what the spec requires. It is on by default,
it is configurable, and the option that switches it off restores conformance.

=over 4

=item * B<A cap on receives answered with a synthesized disconnect event.>

B<Spec text.> L<PAGI::Spec::Www/"Disconnect - receive event"> (websocket) and
L<PAGI::Spec::Www/"SSE Disconnect - receive event">: "Once this event has been
delivered the scope is over, and a further C<receive()> resolves with the same
event again." The http scope's L<PAGI::Spec::Www/"Disconnect - receive event">
says the same in fewer words: the event is "sent to the application if receive
is called after a response has been sent or after the HTTP connection has been
closed". Nothing in the spec limits how many times.

B<What PAGI::Server does instead.> It re-delivers the event, and counts the
re-deliveries. After C<max_disconnect_receives> of them on one scope -- 100 by
default -- the next C<receive()> Future B<fails> rather than resolving, which
raises in the application and ends the scope. One error line is logged for the
scope; later calls fail silently. Only synthesized answers count: the scope's
queued disconnect event, and receives already pending when the disconnect was
detected, are ordinary deliveries.

B<Why.> Measured on 2026-09-10: an application whose receive loop never checks
for the event ran 900,825 iterations inside a single turn of the event loop,
because each answer came from an already-resolved Future and nothing yielded --
during which a second, unrelated HTTP client on the same process received no
response at all. Failing the call costs the one broken scope; re-delivering
without limit costs every connection in the process.

B<The option.> C<< PAGI::Server->new(max_disconnect_receives => $count) >>,
C<configure>, or C<--max-disconnect-receives>. C<0> removes the cap and
restores strict conformance. Pinned by C<t/75-max-disconnect-receives.t>,
which asserts the capped behaviour, the unlimited behaviour under C<0>, and
that neither pending receives nor the abandoned-Future race are affected.

=back

Section 6.3.3 and closes the CL/TE desync that enables HTTP request smuggling.

=head2 HTTP/2 Features

=over 4

=item * ALPN negotiation (h2, http/1.1)

=item * Stream multiplexing (100 concurrent streams default)

=item * HPACK header compression (93.7% space savings observed)

=item * Flow control (per-stream and connection-level)

=item * Stream state validation (END_STREAM tracking, RST_STREAM on violations)

=item * Extended CONNECT for WebSocket over HTTP/2 (RFC 8441)

=item * Server SETTINGS: configurable max_concurrent_streams, initial_window_size,

=item * A request HEADERS block exceeding max_header_list_size gets a real

=item * C<http.fullflush> on HTTP and SSE streams

=back

Filehandle (C<fh>) response bodies are read B<synchronously>, in fixed-size
chunks inside the connection's own send loop, on both HTTP/1.1 and HTTP/2 --
the handle is application-owned and cannot be handed to the async worker
pool across a fork boundary. This differs from C<file> (path) bodies opened
by the server, which use the async worker pool (L<PAGI::Server::AsyncFile>)
for files larger than C<sync_file_threshold>; a C<fh> body bypasses that
pool regardless of size.

=head2 Transport Flow Control (pagi.transport)

PAGI exposes outbound flow-control introspection to applications through the
C<pagi.transport> scope key (see L<PAGI::Spec::Www/"Transport Flow Control">):
C<buffered_amount>, the high/low watermarks, and the
C<on_high_water>/C<on_drain> backpressure callbacks. Over HTTP/2 the handle
measures the B<per-stream> send backlog, so each multiplexed stream is bounded
independently.

PAGI::Server provides C<pagi.transport> for every streaming scope type on both
transports: C<http> (streaming responses), C<sse>, and C<websocket>, on both
HTTP/1.1 and HTTP/2. The HTTP/2 WebSocket send path frames application
messages, protocol replies (pong, the close-frame echo), and its own keepalive
ping through the same per-stream send queue and pull-based data-provider model
that HTTP/2 streaming and SSE use. From the application's perspective the
transport is invisible: a WebSocket app sees the same C<pagi.transport>
surface and semantics -- C<buffered_amount>, the high/low watermarks,
C<on_high_water>/C<on_drain> -- whether the connection is HTTP/1.1 or
HTTP/2.

C<on_drain> fires only for a genuine drain -- the buffer actually falling
back below the low mark -- on both transports. Tearing a connection down
while the buffer is still above the high mark (client disconnect, timeout,
server shutdown, ...) does not fire C<on_drain>: the connection is going
away, not draining. A producer parked on the blocking backpressure path
(a C<$send> awaiting the buffer to drain) still resumes on teardown, so no
coroutine is left hanging; only the app-facing hysteresis callback is
withheld.

=head2 WebSocket over HTTP/2 (RFC 8441)

PAGI::Server accepts a WebSocket over HTTP/2 through RFC 8441 Extended
CONNECT (C<:protocol =E<gt> 'websocket'>). Each accepted stream carries its
own C<websocket.*> event stream, multiplexed with every other stream on the
connection, and its own C<pagi.connection>.

B<Framing.> RFC 8441 section 4 makes the framing identical to HTTP/1.1, so
the same RFC 6455 checks apply per stream: a nonzero RSV bit, a reserved
opcode, or a control frame over 125 bytes closes that stream with C<1002>
and delivers C<websocket.disconnect> with reason C<protocol_error>. Pinned
by C<t/http2/37-ws-frame-validation.t>.

B<Keepalive.> C<websocket.keepalive> runs per stream, with its timers on the
stream rather than the connection. A missing pong closes only that stream,
with the code and reason the spec names (C<1006> / C<keepalive_timeout>);
no Close frame is written, because RFC 6455 section 7.4.1 forbids C<1006>
on the wire, and the stream is reset (RFC 8441 section 5). Pinned by
C<t/http2/31-ws-keepalive-disconnect.t>.

B<Disconnect.> The C<code> / C<reason> pairs are the ones
L<PAGI::Spec::Www/"Disconnect - receive event"> defines. Where the spec
leaves the close code to the server, PAGI::Server uses the RFC 6455 section
7.4.1 code for the fault: C<1002> for a framing or protocol error, C<1007>
for invalid UTF-8, and C<1008> (policy violation) when the stream's receive
queue overflows C<max_receive_queue>. The event is queued exactly once per
stream, whichever closure path fires first; a further C<receive()> resolves
with the same event again, with a peer's Close code and text intact, and a
completed refusal delivers none (see L</"PAGI SPECIFICATION RULINGS">).
Pinned by C<t/http2/31> (queued once, proven through
C<max_disconnect_receives>), C<t/http2/43-receive-after-stream-end.t>
(re-delivery), C<t/70-protocol-disconnect-matrix.t> (every scope type
against every ending, both transports) and C<t/74-h2-ws-clean-end.t> (the
clean-end classification).

=head2 HTTP/2 Trailers (http.response.trailers)

When an HTTP/2 response start declares C<trailers =E<gt> 1>, a terminal body
event does not end the stream: the final C<DATA> frame carries no
C<END_STREAM>. A following C<http.response.trailers> event submits a
trailing C<HEADERS> block that carries C<END_STREAM>, completing the
response; an empty or absent C<headers> list is valid and still terminates
the stream. On a HEAD request the trailers event is validated and discarded
rather than transmitted -- HEAD sends no body, so nothing needs to reach the
wire, but the response still completes normally.

The trailer field list goes through the same connection-specific-header
strip as every other HTTP/2 response path (see "HTTP/2 Connection-Specific
Header Stripping" below): an application-supplied C<Connection>,
C<Keep-Alive>, C<Proxy-Connection>, C<Transfer-Encoding>, C<Upgrade>, or
C<TE> field is removed from the trailer block before submission, with a
warning logged per stripped occurrence. Unlike a response's own C<HEADERS>,
a trailer block carries no C<TE>-with-C<trailers> carve-out -- RFC 9110
section 6.6.2 forbids every connection-specific field from a trailer section
outright, so a trailer-borne C<TE> is stripped unconditionally.

Because the trailing C<HEADERS> must not be submitted ahead of body data the
peer hasn't yet received, a C<send()> carrying C<http.response.trailers> can
remain pending for as long as the peer withholds HTTP/2 flow-control window
on the still-draining body: trailers participate in the same per-stream
backpressure as ordinary body sends. The Future still resolves once nghttp2
accepts the trailing C<HEADERS> submission, the same "accepted, not
necessarily delivered" semantics every other HTTP/2 send Future uses.

A response that declares C<trailers =E<gt> 1> and then returns, or throws,
without ever sending C<http.response.trailers> is an incomplete response
under the same rule that governs an unsent terminal body chunk (see
"Application Left a Response Incomplete" below): the stream is reset
(C<RST_STREAM>, C<INTERNAL_ERROR>) rather than left open or closed as if
nothing were missing, so the incompleteness is observable to the client.

PAGI::Server also accepts request trailers from the client -- a C<HEADERS>
block following the request's initial headers and any C<DATA> frames (RFC
9113 section 8.1). PAGI::Server accumulates the field list from nghttp2's own
C<on_header> callback -- nghttp2 itself, not a PAGI-side check, is what
enforces the field is well-formed at the HPACK/HTTP-messaging layer before
that callback ever fires -- and then discards it: PAGI defines no
request-trailer receive event yet, so an application never sees them. If
C<END_STREAM> rides the trailer C<HEADERS> instead of a C<DATA> frame, the
request body still completes normally for the application. A pseudo-header
field in a trailer block is malformed under RFC 9113 section 8.1;
PAGI::Server's own callback layer rejects it as a defense-in-depth check,
though in practice a conforming client cannot construct one and get it as
far as PAGI's code: nghttp2's own HTTP-messaging validation catches a
pseudo-header in a trailer block first, at the C library layer, and tears
down the whole connection (C<GOAWAY>) rather than only the offending stream.

=head2 HTTP/2 Oversized Request Headers (RFC 9113 section 10.5.1)

When a request's HEADERS block exceeds C<max_header_list_size>, PAGI::Server
sends a real HTTP 431 (Request Header Fields Too Large) response rather than
a bare C<RST_STREAM> with no C<:status> at all -- matching both RFC 9113
section 10.5.1 ("a server that receives a larger header block than it is
willing to handle can send an HTTP 431") and PAGI::Server's own HTTP/1.1
behavior for the same condition.

HPACK decoding of the oversized block is allowed to run to completion
instead of being aborted mid-frame: nghttp2's dynamic table stays
consistent, and PAGI simply stops storing fields for a block it will not
dispatch once the running RFC 7541 accounting (C<name_len + value_len + 32>
per field) crosses the limit. The 431 is synthesized once the C<HEADERS>
frame commits; the request is never delivered to the application (no
C<on_request> dispatch, no C<pagi.connection>, no receive-queue state).

If a client sends request trailers (a later C<HEADERS> block, see "HTTP/2
Trailers" above) after headers that were already too large to dispatch, the
trailer block is still classified normally by the pending-block machinery
and is harmlessly discarded (or, if the trailer block is itself oversized,
handled by the case below) -- it never causes a crash or a second dispatch.

This applies to the request's initial HEADERS block only. A trailer
HEADERS block that is itself oversized keeps its original, unchanged
behavior: the pending trailer block is discarded and the stream is reset
(C<RST_STREAM>), since by that point a response may already be in flight
and there is no request-trailer receive event for an application to see
in the first place (see "HTTP/2 Trailers" above).

=head2 Connection State (pagi.connection)

PAGI::Server provides C<pagi.connection> on every scope, on both
transports, with every accessor L<PAGI::Spec::Www/"Connection State">
requires, marked before any pending C<receive()> is resumed and carrying the
same token as the scope's disconnect event. On HTTP/2 each stream has its
own object; a whole-connection teardown (shutdown, socket error) records the
connection-level reason on every stream still open, so a stream
mid-response when the connection dies still reports why. Coverage:
C<t/69-connection-state-protocol-scopes.t>, C<t/70-protocol-disconnect-matrix.t>
(agreement asserted per cell), C<t/http2/30-connection-state.t>,
C<t/72-abort.t> and C<t/http2/41-abort.t> (C<abort> on every scope type,
including a send parked on backpressure and a sibling HTTP/2 stream that
survives), C<t/69>, C<t/55-sse-alignment.t>, C<t/http2/24-incomplete-response.t>
and C<t/http2/42-d13-incomplete-session.t> (responses left incomplete).

Two details the spec leaves to the server:

=over 4

=item * C<disconnect_future> returns a fresh, cancellation-isolated observer
on every call. After an abnormal end it is already resolved with the reason;
after a clean end it stays pending forever, since there is no reason to
resolve it with.

=item * C<write_timeout> is B<not currently produced>. PAGI::Server has no
timer on an individual write; a stalled write is caught, if at all, by
C<timeout> or C<request_timeout>. Socket errors other than a clean EOF
report C<read_error> / C<write_error>.

=back

=head1 SERVER-SENT EVENTS (SSE)

PAGI::Server implements Server-Sent Events per L<PAGI::Spec::Www> on both
HTTP/1.1 and HTTP/2, sharing behavior across transports wherever the wire
format allows it.

=head2 Connection Detection

A request is classified as an C<sse> scope by a boolean client-signal check
on the combined values of all C<Accept> headers, parsed as a comma-separated
list of media ranges (RFC 9110 Section 12.5.1):

=over 4

=item * the C<sse> scope is assigned iff the exact range
C<text/event-stream> appears, case-insensitively, with an effective quality
value greater than zero;

=item * C<q=0> is an explicit refusal and never signals SSE;

=item * wildcard ranges (C<*/*>, C<text/*>) never signal SSE;

=item * media-type parameters other than C<q> are ignored for the test.

=back

This is a light parse shared identically by both transports -- not full
content negotiation, which stays application/middleware territory. It
applies regardless of HTTP method: a C<GET>, or a C<POST> from the
fetch-event-source/datastar request-then-stream pattern, both classify the
same way.

=head2 UTF-8 Wire Encoding

C<sse.send> string fields, C<sse.comment> text, and server-generated
keepalive comments are formatted as characters and then encoded to UTF-8
exactly once, at the wire boundary, before queueing or HTTP/1.1 chunk
framing. For an application-initiated send (C<sse.send> or C<sse.comment>),
a Perl string that cannot be encoded fails that send's Future instead of
writing corrupted bytes to the socket. Chunk lengths, per-stream send-queue
byte counts, and transport watermarks are all measured on the
already-encoded byte string.

An C<sse.keepalive> event's optional C<comment> field is checked for the
same encodability, but at arm time -- when the C<sse.keepalive> event
itself is sent, not deferred to the keepalive timer's first tick.
C<EventValidator> requires a present C<comment> to be a defined,
non-reference string that round-trips
C<Encode::encode('UTF-8', $comment, Encode::FB_CROAK)>, croaking
C<"sse.keepalive 'comment' must be a UTF-8-encodable string"> otherwise. An
unencodable comment therefore fails the send Future that armed the
keepalive, rather than escaping as an uncaught die inside the timer tick.

=head2 Request Bodies

C<sse.request> (the event an application receives when it reads the body of
a POST/PUT SSE request) shares its body-reading semantics with ordinary HTTP
requests rather than a separate partial parser:

=over 4

=item * HTTP/1.1 supports both C<Content-Length> and chunked
C<Transfer-Encoding> bodies, through the same body reader C<http.request>
uses;

=item * C<Expect: 100-continue> is handled transparently -- the server sends
C<100 Continue> before waiting for body data;

=item * HTTP/2 waits for the stream's C<DATA> frames and C<END_STREAM>
before delivering the (one-shot) C<sse.request> event, so a body still
arriving across frames is never reported early behind a truthful-looking
C<more =E<gt> 0>;

=item * an empty-body request receives one empty terminal event, and
disconnect stays observable once the body is complete.

=back

=head2 Per-Stream HTTP/2 Keepalive and Idle Timeout

As with HTTP/2 WebSocket (see L</"WebSocket over HTTP/2 (RFC 8441)">), an HTTP/2 connection
multiplexes many SSE streams, so C<sse.keepalive> and C<sse_idle_timeout>
state -- timer, interval, comment, writer, and last-activity reset -- live
on the individual stream, not the connection. Starting or updating
keepalive on one stream cannot stop, replace, or redirect another stream's
timer, and an idle-timeout expiry ends only that stream (the server marks
it closing, flushes any already-queued data, then sends the final
C<END_STREAM> frame -- the same path an application-initiated C<sse.close>
takes). Sibling streams and the connection itself are unaffected.

Over HTTP/1.1, one connection carries only one SSE stream at a time, so
C<sse_idle_timeout> is enforced at the connection level there: expiry closes
the connection outright.

=head2 Response Headers

On C<sse.start> the server supplies C<Content-Type>, C<Cache-Control>, and
C<Date> only when the application did not already set them; an
application-supplied value for any of these is sent as-is, not duplicated
alongside a server default. C<Connection: keep-alive> on HTTP/1.1 is the
exception: it is a framing header the protocol requires the server to
control, so it is always advertised regardless of what the application
sent. HTTP/2 never emits an HTTP/1-only C<Connection> header or a
C<Transfer-Encoding> (chunked-framing) header -- an HTTP/2 SSE stream is
framed as DATA frames via C<submit_response_streaming>, which carries no
such headers.

The C<Date>-only-when-absent rule above holds server-wide, not only for
C<sse.start>: on every response path, the server supplies a plain C<Date>
header only when a C<Date> is not already present; where the application
supplies its own header list, an application-supplied C<Date> is always
honored as-is instead of being duplicated. This spans both transports and
every response shape the server can emit:

=over 4

=item * B<Normal application responses> -- C<http.response.start> on
HTTP/1.1 and HTTP/2 (including the HTTP/2 HEAD-request path, which reuses
the same header list), and C<sse.start> on both transports (above).

=item * B<Refusals> -- the C<http.response.start> that refuses a WebSocket
handshake or an SSE stream, on both transports. A refusal is an ordinary HTTP
response and gets the ordinary HTTP response path's header handling.

=item * B<Server-generated responses, which carry no application header
list to check> -- the HTTP/1.1 synthesized error response (e.g. the
unanswered-request C<500> backstop and the bare WebSocket-handshake
rejection, which both share that same path); and, HTTP/2 only, the bare
WebSocket-handshake-rejection C<403>, the C<413> request-precheck
rejection, the C<413> body-size-overrun rejection, the synthesized
C<500>, and the plain (non-Extended-CONNECT) C<CONNECT> method's C<501>
rejection.

=back

=head2 HTTP/2 Connection-Specific Header Stripping

RFC 9113 section 8.2.2 forbids connection-specific header fields on
HTTP/2: an application-supplied C<Connection>, C<Keep-Alive>,
C<Proxy-Connection>, C<Transfer-Encoding>, or C<Upgrade> header -- or a
C<TE> header carrying anything but the exact token C<trailers> -- corrupts
the response at the framing layer (nghttp2 rejects the header list; the
client receives only the C<:status> pseudo-header, with no body).
PAGI::Server strips these six header names, case-insensitively, from
application-supplied response headers before they reach nghttp2, on every
HTTP/2 response path that maps application headers: C<http.response.start>
(including the HEAD-request path, which reuses the same header list),
C<sse.start>, C<websocket.accept>, and the trailing C<HEADERS> block
submitted by C<http.response.trailers> (see "HTTP/2 Trailers" above). A
refusal on a websocket or sse scope is covered by the
C<http.response.start> entry, being an ordinary HTTP response.

C<TE> is the one carve-out, and it applies only to a response's own
C<HEADERS> block, where it advertises that trailers are coming: a C<TE>
header whose value -- after trimming leading/trailing optional whitespace
(OWS) -- is exactly the token C<trailers> is kept there; any other C<TE>
value, including a compound value like C<trailers, gzip>, is stripped. That
carve-out does not extend inside a trailer block itself -- RFC 9110 section
6.6.2 forbids every connection-specific field, C<TE> included, from a
trailer section outright, so C<http.response.trailers> strips a
trailer-borne C<TE> unconditionally, regardless of its value. Each stripped
occurrence, not deduplicated by name, logs C<PAGI: connection-specific
header '$name' stripped from HTTP/2 response (RFC 9113)> for a response
header, or C<PAGI: connection-specific header '$name' stripped from HTTP/2
trailers (RFC 9113)> for a trailer field.

HTTP/1.1 performs a narrower, separate strip of its own -- see the next
section.

=head2 HTTP/1.1 Connection-Specific Header Stripping

The PAGI specification states: "Over HTTP/1.1 the server must ignore or
strip application-supplied Transfer-Encoding and Connection -- it supplies
its own -- and SHOULD log when it does." Unlike the HTTP/2 strip above,
this covers only two header names, C<Transfer-Encoding> and C<Connection>
-- HTTP/1.1 has no prohibition on C<Keep-Alive>, C<Proxy-Connection>,
C<Upgrade>, or C<TE> as ordinary application response headers, so those
four remain untouched.

PAGI::Server strips C<Transfer-Encoding> and C<Connection>,
case-insensitively, from application-supplied response headers before they
reach the wire, on every HTTP/1.1 response path that maps application
headers: C<http.response.start> (which is also how a websocket or sse scope
is refused), C<sse.start>, and the extra headers an application supplies on
C<websocket.accept>.
Before this strip, an application-supplied C<Transfer-Encoding> could
duplicate or conflict with the server's own framing decision (two
C<Transfer-Encoding> lines, or C<Transfer-Encoding> alongside
C<Content-Length>), and an application-supplied C<Connection> could
duplicate the server's own forced C<Connection: keep-alive> on
C<sse.start>, contradict the C<Connection: close> a refusal carries, or
duplicate the server's own C<Connection: Upgrade>
on a C<websocket.accept> 101 response (that line is constructed separately
and is itself untouched -- RFC 6455 requires it). Each stripped occurrence,
not deduplicated by name, logs C<PAGI: connection-specific header '$name'
stripped from HTTP/1.1 response>.

The same two-name strip also applies to C<http.response.trailers>, on its
own trailer header list, before the trailer block reaches the wire. RFC
9110 section 6.5.1 forbids connection-specific fields in trailers outright,
on any HTTP version -- not only the PAGI spec's h1 response-header rule
above, so an application-supplied C<Transfer-Encoding> or C<Connection>
trailer field is stripped the same way an application-supplied
C<http.response.start> header is, logging the same C<PAGI:
connection-specific header '$name' stripped from HTTP/1.1 response> line.
Unlike the HTTP/2 strip, HTTP/1.1 trailers get no separate log message for
the trailer context, and no C<TE> carve-out is relevant here -- C<TE> is
not one of the two names HTTP/1.1 strips at all.

=head2 Connection Reuse after a Clean Stream End (HTTP/1.1)

C<sse.start> advertises C<Connection: keep-alive>, and the server honors it.
An HTTP/1.1 SSE stream ends B<cleanly> only when the application sends
C<sse.close>; that is the stream's terminal event, and a plain return without
it is an incomplete response rather than a clean end. On C<sse.close> the
server writes the chunked terminator, resets the per-request state the stream
accumulated, and hands the connection back to ordinary keep-alive request
handling, including serving any request already pipelined in the read buffer.
A pooled client (browser, C<Net::Async::HTTP>, curl) can therefore reuse the
same socket for its next request, which matters for the short
POST-SSE-exchange pattern used by fetch-event-source and datastar.

Keep-alive yields to the usual overrides, each of which closes the
connection the same way it does outside SSE: a client C<Connection: close>,
HTTP/1.0 semantics, server shutdown, an application exception, a
B<completed refusal> (it always closes the connection -- no event stream was
ever started -- and tells a pooling client so with an explicit
C<Connection: close> header), and any B<abnormal> end (client disconnect,
idle timeout, write error, C<abort>, or a stream the application abandoned
without C<sse.close>). An abnormal end is also the only thing that delivers
C<sse.disconnect> to the application; a clean end never does. This includes a
completed refusal: it is not an abnormal end, so it delivers no
C<sse.disconnect> either -- an application that calls C<receive()> again after
its refusal response has already finished (before returning) gets no event at
all; the call parks rather than resolving with a synthesized disconnect.

A refusal streams like any other HTTP body: with C<more =E<gt> 1> the server
writes each chunk as it is sent rather than buffering the response until the
application finishes, and the connection closes once the refusal's terminal
event has been written.

An application that returns without ever answering the request at all --
no C<sse.start> and no refusal -- does not reach the keep-alive path. That is
the same protocol error the plain HTTP path reports: the server logs one error
line, synthesizes a C<500> response if the client is still connected, logs the
access entry, and closes the connection. A refusal that started
(C<http.response.start>) but never sent its terminal body or trailers is an
incomplete response and takes the abnormal path instead, reporting
C<server_error>.

=head1 RECOMMENDATIONS

=head2 Production Deployment

For production deployments, consider:

=over 4

=item 1.

Use a reverse proxy (nginx, HAProxy) for TLS termination, rate limiting,
and per-IP connection limits.

=item 2.

Enable the L<PAGI::Middleware::SecurityHeaders> middleware for security headers.

=item 3.

Set appropriate limits for your use case:

    my $server = PAGI::Server->new(
        timeout           => 60,      # Connection idle timeout
        max_header_size   => 8192,    # 8KB header limit
        max_header_count  => 100,     # Max headers per request
        max_body_size     => 10_000_000,  # 10MB body limit
        max_ws_frame_size => 1_000_000,   # 1MB WebSocket frames
        shutdown_timeout  => 30,      # Graceful shutdown timeout
    );

=back

=head2 Performance Optimization

For optimal performance on macOS, set the EV backend to kqueue:

    LIBEV_FLAGS=8 pagi-server --loop EV --app myapp.pl
